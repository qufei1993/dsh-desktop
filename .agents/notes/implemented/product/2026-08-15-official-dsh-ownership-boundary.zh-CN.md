# Decision: 官方 DSH 行为和数据不属于 Desktop 所有权

Status: implemented
Category: product

[English](2026-08-15-official-dsh-ownership-boundary.md) | 简体中文

## 问题

桌面壳很容易因为修改内置包、注入 UI、依赖私有 API，或者接管官方配置与用户数据而变成非官方 fork。这会产生不兼容行为，并让支持责任变得模糊。

## 决定

DSH Desktop 只拥有内置运行时、精确的官方 DSH 安装、应用状态、进程托管、桌面窗口和自身更新通道。它不 fork、patch、重新编译、注入或导入官方 DSH 私有模块，也不管理 DSH 模型、凭据、会话、插件、Skills、MCP、权限、配置或用户数据。生产代码不覆盖 `DSH_HOME`。

## 考虑过的替代方案

**修补不兼容的官方版本。** 这可能暂时隐藏上游问题，但会产生行为和支持责任都不同于官方 DSH 的私有分发版本。

**在 Desktop 管理器中公开 DSH 配置。** 这会重复官方所有权，需要追踪私有格式，并可能损坏或错误表达用户数据。

**向官方 Web 页面注入桌面控件。** 这会让桌面壳依赖官方 DOM 和实现细节，并改变项目承诺保持不变的界面。

## 影响

DSH Desktop 不能私下修复官方数据或插件兼容问题，必须如实显示上游失败。作为交换，官方行为的责任归属保持清晰，版本可以独立替换，社区桌面壳保持狭窄维护边界。

## 验证

`npm run audit:boundary` 检查生产源码中的禁止导入和部分不安全配置。官方与安装包冒烟测试通过公开 CLI 启动未修改的包，并验证官方启动标记。
